# گزارش جامع قابلیت‌های پیاده‌سازی‌شده دیدبان مالی

**مبنای گزارش:** کد موجود در شاخه و working tree فعلی  
**تاریخ بازبینی:** ۱۴۰۵/۰۷/۰۱  
**نسخه محصول:** `0.1.0`

## ۱. خلاصه اجرایی

دیدبان مالی یک سامانه چندشرکتی برای دریافت فایل‌های مالی، تبدیل آن‌ها به مدل داده یکپارچه، تحلیل عملکرد، تطبیق بانک و حسابداری، کشف مغایرت و ریسک، رسیدگی انسانی، گزارش‌گیری و پایش نقدینگی است. محصول جایگزین نرم‌افزار حسابداری نیست؛ روی داده‌های حسابداری، بانک و فروش قرار می‌گیرد و از آن‌ها خروجی قابل ردیابی و تصمیم‌پذیر می‌سازد.

در وضعیت فعلی، زنجیره اصلی زیر در کد پیاده‌سازی شده است:

`ثبت‌نام و شرکت ← بارگذاری فایل ← اسکن و قرنطینه ← نگاشت و اعتبارسنجی ← نرمال‌سازی ← تحلیل مالی ← تطبیق ← یافته و شاهد ← بررسی انسانی ← داشبورد و PDF`

علاوه بر MVP اولیه، ماژول‌های خزانه‌داری و نقدینگی، دریافتنی‌ها، پرداختنی‌ها، هشدار زودهنگام، شبیه‌سازی سناریو و حذف اسناد واردشده نیز اضافه شده‌اند.

## ۲. معماری و زیرساخت

- مخزن به‌صورت monorepo و شامل وب، API، migration، داده دمو، اسکریپت و مستندات است.
- رابط کاربری با Next.js 16، React 19، TypeScript، Tailwind CSS و اجزای Radix/shadcn ساخته شده است.
- بک‌اند یک modular monolith مبتنی بر FastAPI و SQLAlchemy async است.
- PostgreSQL پایگاه داده اصلی و مرز جداسازی شرکت‌ها است.
- Redis برای broker و result backend صف استفاده می‌شود.
- Celery پردازش‌های طولانی مانند اسکن، نرمال‌سازی، تحلیل، تطبیق، یافته و PDF را اجرا می‌کند.
- MinIO/S3 فایل اصلی و خروجی PDF را در bucket خصوصی نگه می‌دارد.
- ClamAV فایل‌های ورودی را پیش از استفاده اسکن می‌کند.
- Alembic شامل ۱۶ مرحله migration از زیرساخت اولیه تا هشدار، شبیه‌سازی و حذف سند است.
- Docker Compose سرویس‌های PostgreSQL، Redis، MinIO، ClamAV، migration، API، worker و web را بالا می‌آورد.
- API دارای liveness، readiness، شناسه درخواست، CORS، `nosniff` و سیاست referrer است.
- محیط Fly.io و proxy وب برای استقرار نیز در پروژه تعریف شده است.

## ۳. هویت، نشست و دسترسی چندشرکتی

### قابلیت‌های هویت

- ثبت‌نام کاربر و ایجاد فضای کاری اولیه
- ورود، خروج، بازیابی نشست و endpoint مشاهده کاربر جاری
- access token کوتاه‌عمر و refresh token چرخشی
- نگهداری hash نشست و refresh token در پایگاه داده
- کوکی HttpOnly و محافظت double-submit CSRF برای درخواست‌های تغییردهنده
- هش رمز عبور با Argon2
- هدایت خودکار کاربر مهمان به ورود و کاربر واردشده به اولین شرکت یا ساخت شرکت

### شرکت و اعضا

- ایجاد، فهرست، مشاهده و ویرایش شرکت
- نگهداری نام حقوقی، شناسه ملی، ارز، ماه شروع سال مالی و منطقه زمانی
- انتخاب و جابه‌جایی بین شرکت‌ها از رابط
- افزودن عضو با ایمیل، تغییر نقش و حذف عضو
- محافظت از حذف یا تنزل آخرین مالک
- نقش‌های `OWNER`، `FINANCE_MANAGER`، `ADVISOR` و `VIEWER`
- کنترل مجوز هم در routeها و هم در PostgreSQL

### جداسازی داده

- همه موجودیت‌های مالی با `company_id` محدود می‌شوند.
- Row Level Security برای جدول‌های حساس فعال و اجباری شده است.
- کاربر پایگاه داده برنامه superuser یا دارای bypass RLS نیست.
- کلیدهای خارجی مرکب از اتصال رکوردهای متعلق به دو شرکت جلوگیری می‌کنند.
- دسترسی به منبع شرکت دیگر عموماً با ۴۰۴ پنهان می‌شود.
- عملیات مهم در audit event ثبت می‌شوند.

## ۴. ورود و مدیریت اسناد مالی

### دریافت فایل

- پشتیبانی از CSV و XLSX برای سه منبع حسابداری، بانک و فروش
- بارگذاری streaming تا سقف پیش‌فرض ۵۰ مگابایت
- محدودیت پیش‌فرض ۲۵۰ هزار ردیف
- پاک‌سازی نام فایل و تولید object key تصادفی
- محاسبه SHA-256 و تشخیص فایل تکراری
- ذخیره اولیه در قرنطینه و انتقال فایل سالم به فضای خصوصی
- اسکن ClamAV با retry کنترل‌شده هنگام عدم دسترسی موقت
- رد فایل اجرایی تغییرنام‌یافته، XLSX خراب، آرشیو مشکوک و فایل ماکرو‌دار
- نمایش وضعیت زنده upload و scan در رابط
- دانلود فایل فقط پس از پاک اعلام‌شدن و فقط برای اعضای شرکت

### پیش‌نمایش، نگاشت و اعتبارسنجی

- انتخاب sheet و ردیف سرستون فایل اکسل
- پیش‌نمایش ردیف‌ها پیش از ثبت
- پیشنهاد نگاشت ستون‌های فارسی و انگلیسی متناسب با نوع منبع
- الزام تأیید دستی نگاشت؛ پیشنهاد به‌طور خودکار نهایی نمی‌شود.
- تأیید صریح تقویم شمسی/میلادی و واحد ریال/تومان
- تبدیل ارقام فارسی و عربی، حذف جداکننده هزارگان، parse تاریخ و تبدیل تومان به ریال
- ذخیره نسخه تغییرناپذیر نگاشت و پروفایل قابل استفاده مجدد
- نگهداری ردیف خام، شماره sheet/row و hash برای lineage
- خطاهای سطح فایل و ردیف، هشدار، کد خطا، مقدار خام و راه اصلاح
- گزارش تعداد ردیف پذیرفته، ردشده و درصد پوشش
- فهرست و صفحه آماده‌سازی مستقل برای هر import

### ثبت و حذف

- commit غیرهم‌زمان برای نرمال‌سازی و جلوگیری از رکورد تکراری در اجرای مجدد
- وضعیت‌های چرخه واردسازی از upload تا completed، limited یا failed
- حذف import توسط مالک، مدیر مالی یا مشاور و ممنوعیت حذف برای مشاهده‌گر
- پاک‌سازی object ذخیره‌شده و داده‌های وابسته با ثبت رخداد ممیزی
- dialog تأیید حذف و حالت پردازش در رابط

## ۵. مدل مالی یکپارچه و lineage

مدل کانونیکال پیاده‌سازی‌شده شامل موارد زیر است:

- حساب و تاریخچه طبقه‌بندی حساب
- سند و آرتیکل حسابداری
- حساب بانکی و تراکنش بانکی
- طرف حساب
- فاکتور فروش
- ارتباط مستقیم رکوردهای مالی با `source_row` و فایل اصلی

رفتارهای اصلی:

- مبلغ کانونیکال به ریال و با نوع decimal ذخیره می‌شود.
- تاریخ مالی نهایی میلادی است و متن خام ورودی از بین نمی‌رود.
- متن فارسی برای جست‌وجو و تطبیق نرمال می‌شود.
- شماره شبا mask می‌شود و فقط چهار رقم انتهایی برای نمایش باقی می‌ماند.
- سندهای نامتوازن شناسایی و در پوشش داده منعکس می‌شوند.
- نرمال‌سازی chunked و idempotent است.
- حساب‌ها بر اساس کد و نام به طبقات دارایی، بدهی، حقوق مالکانه، درآمد و هزینه نگاشت می‌شوند.

نکته وضعیت فعلی: route و صفحه مستقل «مدل مالی/طبقه‌بندی دستی حساب» در working tree فعلی حذف شده‌اند؛ مدل داده و منطق طبقه‌بندی در بک‌اند باقی است، اما این گردش دیگر صفحه مستقل قابل استفاده ندارد.

## ۶. تحلیل مالی دوره‌ای

- ساخت اجرای تحلیل برای بازه تاریخ مشخص و با `Idempotency-Key`
- صف، پردازش پس‌زمینه، وضعیت پایدار، retry و بازیابی اجرای قبلی
- snapshot ورودی شامل batchهای منبع، شمار آرتیکل‌ها، دوره و نسخه قواعد
- خروجی‌های محاسبه‌شده:
  - درآمد
  - هزینه
  - سود خالص
  - حاشیه سود خالص
  - کل دارایی
  - کل بدهی
  - حقوق مالکانه
  - خالص حرکت نقد
  - فروش صورتحساب‌شده
  - مبلغ وصول‌شده
  - مانده فروش
- مقدارهای پولی و نسبت‌ها در API به‌صورت رشته decimal سریال می‌شوند تا خطای عددی JavaScript ایجاد نشود.
- پوشش حسابداری، بانک و فروش و دلیل نبود هر شاخص جداگانه گزارش می‌شود.
- در نبود داده کافی، خروجی `completed_limited` تولید می‌شود و سامانه عدد ساختگی نمی‌سازد.
- رابط انتخاب دوره، شروع تحلیل، polling وضعیت، نمایش metricها، محدودیت‌ها و snapshot را دارد.

## ۷. تطبیق بانک و حسابداری

- اجرای تطبیق غیرهم‌زمان روی snapshot تحلیل و تنظیمات نسخه‌دار
- exact match فقط در صورت مبلغ، تاریخ و هویت متنی/مرجع سازگار و نامزد یکتا
- تشخیص duplicate قطعی با شناسه منبع و duplicate احتمالی با fingerprint
- کاندیدسازی قاعده‌ای بر اساس مبلغ، فاصله روز کاری، reference و شباهت شرح
- امتیازدهی تا ۱۰۰ با اجزای مبلغ، تاریخ، reference و شباهت متن
- fuzzy candidate فقط به‌صورت `potential_match` و نیازمند بررسی انسان
- جلوگیری از auto-match در وضعیت مبهم
- ثبت اختلاف مبلغ، اختلاف تاریخ، ویژگی‌های امتیاز و شواهد دو طرف
- محدودیت پذیرش چندگانه یک رکورد با ایندکس‌های یکتا
- فیلتر و مشاهده runها و matchها در رابط
- پنل رتبه‌بندی معنایی AI فقط برای مجموعه نامزدهای از قبل محدودشده

## ۸. موتور یافته، اولویت و شواهد

سامانه دقیقاً هشت کد یافته مصوب را تولید می‌کند:

1. تراکنش احتمالاً مفقود
2. تراکنش تکراری
3. مغایرت مبلغ
4. مغایرت تاریخ
5. افت درآمد
6. افت سود
7. رشد هزینه
8. رشد حساب‌های دریافتنی

ویژگی‌های پیاده‌سازی‌شده:

- اجرای تولید یافته به‌صورت queue و idempotent
- استفاده از نتایج تحلیل و تطبیق، بدون دست‌کاری منبع
- جلوگیری از تولید نوع نهم خارج از catalog
- fingerprint پایدار برای جلوگیری از تکرار یافته
- تفکیک `deterministic` و `hypothesis`
- شدت بالا، متوسط و پایین
- امتیاز و band اولویت critical/high/medium/low با نسخه قواعد
- ثبت دلایل قابل توضیح امتیاز
- انواع شاهد: رکورد منبع، مقایسه، محاسبه، قاعده و پوشش
- اتصال شاهد به رکورد کانونیکال، source row، فایل و محاسبه
- فهرست یافته‌ها با فیلتر، جست‌وجو، مرتب‌سازی و صفحه جزئیات
- drawer شاهد و پرونده کامل یافته

- ثبت ممیزی و پشتیبانی از idempotency

- نمایش وضعیت کلی مالی و کیفیت داده
- KPIهای مالی با مقدار قبلی، تغییر مطلق، تغییر نسبی و روند
- خلاصه یافته‌ها بر اساس اولویت و وضعیت گردش کار
- نمایش یافته‌های مهم و محرک‌های اصلی
- امتیاز پوشش داده و محدودیت‌های قابل مشاهده
- اتصال به مسیر جزئیات یافته، تحلیل و گزارش
- کارت‌های تکمیلی نقدینگی، دریافتنی و پرداختنی در داشبورد فعلی

## ۱۱. خزانه‌داری و جریان نقد

### خلاصه نقدینگی

- محاسبه وجه نقد جاری از آخرین مانده بانک، جمع تراکنش‌ها یا حساب‌های نقد و بانک دفتر
- محاسبه نرخ سوخت ماهانه از خروجی ۹۰ روز اخیر یا حساب‌های هزینه
- محاسبه runway بر حسب روز و ماه
- طبقه‌بندی وضعیت runway به بحرانی، هشدار، پایش، سالم یا پایدار
- محاسبه بافر ایمنی
- شناسایی اولین هفته کسری و کمترین مانده پیش‌بینی‌شده

### پیش‌بینی ۱۳ هفته‌ای

- پیش‌بینی هفتگی موجودی آغاز، ورودی، خروجی، تغییر خالص و مانده پایان
- تشخیص کسری و مبلغ کسری هر هفته
- تفکیک منابع ورود و خروج وجه و سهم درصدی آن‌ها
- سناریوهای پایه، بدبینانه و خوش‌بینانه
- سناریوی بدبینانه با کاهش مفروض وصول و افزایش هزینه
- سناریوی خوش‌بینانه با تسریع وصول و صرفه‌جویی هزینه
- نمودار جریان نقد و جدول هفتگی در رابط

بخش خزانه‌داری فعلی چهار زبانه نقدینگی، دریافتنی‌ها، پرداختنی‌ها و تطبیق را در یک workspace تجمیع می‌کند.

## ۱۲. حساب‌های دریافتنی

- محاسبه کل دریافتنی، مبلغ معوق و نسبت معوق
- DSO قطعی و قابل بازتولید بر پایه تأخیر موزون مانده فاکتورها
- سبد سنی جاری، ۱ تا ۳۰، ۳۱ تا ۶۰، ۶۱ تا ۹۰ و بیش از ۹۰ روز
- شمار مشتری و مشتریان پرریسک
- ریز مشتری شامل مانده، مبلغ معوق، نسبت معوق، متوسط تأخیر و تعداد فاکتور باز
- امتیاز ریسک صفر تا ۱۰۰ و سطح low/medium/high/critical
- پیشنهاد اقدام وصول متناسب با سطح ریسک
- ریز فاکتور با مبلغ کل، پرداخت‌شده، مانده، روز تأخیر و bucket
- فیلتر بر اساس مشتری یا bucket و جست‌وجو در رابط

## ۱۳. حساب‌های پرداختنی

- محاسبه کل پرداختنی، مبلغ معوق و نسبت معوق
- سبد سنی بدهی با پنج bucket مشابه دریافتنی
- DPO بر پایه خروجی‌های ۹۰ روز اخیر و fallback کنترل‌شده
- نمایش DSO و چرخه تبدیل وجه نقد با فرمول `CCC = DSO - DPO`
- ریز تأمین‌کننده شامل مانده، معوق، متوسط تأخیر و سهم از کل بدهی
- امتیاز ریسک و پیشنهاد اقدام برای حفظ اعتبار یا جلوگیری از توقف تأمین
- شناسایی بدهی‌های بالای ۶۰ و ۹۰ روز به تأمین‌کنندگان

## ۱۴. هشدارهای زودهنگام

هشت قاعده عملیاتی اکنون ارزیابی و در پایگاه داده همگام می‌شوند:

- runway بحرانی تا ۱۵ روز
- runway هشدار تا ۳۰ روز
- شکاف سرمایه در گردش با CCC بیش از ۴۵ روز
- تمرکز دریافتنی یک مشتری از ۳۵٪ به بالا
- سهم دریافتنی بیش از ۹۰ روز از ۲۰٪ به بالا
- وجود مشتری با امتیاز ریسک حداقل ۷۰
- ریسک توقف تأمین به علت بدهی بالای ۶۰ روز
- انباشت پرداختنی معوق با نسبت حداقل ۳۰٪

سایر قابلیت‌ها:

- شدت critical/warning/info و دسته نقدینگی، ریسک اعتباری، زنجیره تأمین و انطباق
- خلاصه تعداد هشدارها در منوی اصلی
- وضعیت active، acknowledged، resolved و dismissed در مدل
- تأیید مشاهده هشدار همراه با یادداشت
- حل هشدار با ثبت اقدام انجام‌شده
- حل خودکار هشدار فعال در صورت رفع شاخص
- پیشنهاد اقدام و لینک مستقیم به صفحه مرتبط
- تعریف، حذف و تست webhook
- حداقل شدت برای webhook، token اختیاری و log تحویل

محدودیت: ارسال خودکار همه هشدارهای جدید به webhook در background پیاده‌سازی نشده است؛ endpoint تست اتصال و ثبت نتیجه وجود دارد.

## ۱۵. شبیه‌سازی تصمیم مالی

- اجرای what-if بر پایه وضعیت واقعی نقد، دریافتنی و پرداختنی شرکت
- پارامترهای قابل تغییر:
  - تغییر DSO
  - تخفیف تسویه زودهنگام و نرخ پذیرش آن
  - تعداد استخدام و متوسط حقوق
  - تغییر هزینه ثابت ماهانه
  - تغییر DPO
  - شوک تأخیر یا نکول مشتری
- خروجی اثر بر runway، نرخ سوخت، CCC، نقدینگی آزادشده، هزینه تخفیف و سود سالانه
- پیش‌بینی هفتگی مقایسه مبنا و سناریو برای ۱۳ هفته
- verdict مدیریتی فارسی و هشدار ریسک
- سه preset دفاع نقدی، رشد تهاجمی و تست استرس رکود
- ذخیره، فهرست و حذف سناریو
- ماتریس مقایسه چند سناریو با وضعیت مبنا
- تولید PDF یادداشت تصمیم برای هیئت‌مدیره

محدودیت: سرویس ذخیره سناریو در صورت خطای دیتابیس به حافظه process fallback می‌کند. این fallback پس از restart پایدار نیست و خطای پایگاه داده را بیش از حد پنهان می‌کند.

## ۱۶. گزارش PDF

- ساخت snapshot ثابت از اجرای تحلیل تکمیل‌شده
- انتخاب تحلیل با شناسه، دوره یا آخرین اجرای تکمیل‌شده
- ذخیره مرور مالی، یافته‌های مهم، محرک‌ها، پوشش، یادداشت مشاور و وضعیت بررسی
- حفظ یافته‌های کم‌اولویت، ردشده و حل‌شده در ضمیمه
- تولید غیرهم‌زمان و نمایش مرحله و درصد پیشرفت
- PDF فارسی RTL روی A4 با حاشیه ۲۰ میلی‌متر
- ثبت و embed وزن‌های Regular، Medium، Bold و ExtraBold فونت IRANYekanX
- شکل‌دهی درست متن فارسی و ارقام فارسی
- ذخیره خصوصی در MinIO همراه SHA-256 و اندازه فایل
- فهرست، وضعیت، snapshot و دانلود گزارش با کنترل مجوز
- جلوگیری از تولید هم‌زمان با قفل و idempotency
- آرشیو گزارش‌ها و بازیابی پس از refresh
- PDF جداگانه یادداشت تصمیم سناریو نیز پیاده‌سازی شده است.

## ۱۷. AI کنترل‌شده

- تنظیمات append-only در سطح شرکت برای فعال‌سازی AI، توضیح یافته و رتبه‌بندی معنایی
- feature flag سراسری و شرکتی
- توضیح یافته فقط از داده ساخت‌یافته، reason code، اعداد مجاز و شناسه شاهد
- رتبه‌بندی معنایی فقط روی کاندیدهای تطبیق موجود؛ AI حق افزودن نامزد ندارد.
- خروجی schema-bound با `extra=forbid`
- الزام `requires_human_review=true`
- تطبیق تمام اعداد تولیدشده با allowlist
- رد عدد ساختگی، شاهد ناشناخته، confidence جدید یا تغییر مجموعه نامزدها
- timeout و شکست امن بدون اختلال در موتورهای قطعی
- دفتر invocation شامل purpose، prompt version، provider/model، latency، outcome و شاهد
- فهرست و مشاهده invocationها در مرکز کنترل

محدودیت مهم: در کد فعلی فقط `DisabledAiProvider` وجود دارد؛ بنابراین هیچ اتصال واقعی به ارائه‌دهنده خارجی پیاده‌سازی نشده و درخواست‌ها باید با توقف امن ثبت شوند تا ارائه‌دهنده و محل پردازش تصویب شود.

- manifest دارای SHA-256 و ارقام golden

## ۲۲. موارد ناقص، محدود یا نیازمند اصلاح

موارد زیر نباید با قابلیت production-ready اشتباه گرفته شوند:

1. اتصال واقعی AI وجود ندارد و provider عمداً disabled است.
2. صفحه و route مستقل طبقه‌بندی دستی حساب در working tree فعلی حذف شده است.
3. fallback حافظه‌ای سناریوهای ذخیره‌شده پس از restart از بین می‌رود و exceptionهای DB را پنهان می‌کند.
4. webhook فقط ایجاد، حذف و تست می‌شود؛ dispatcher خودکار هشدارها به همه کانال‌ها وجود ندارد.
5. migration فاز ۱۵ برای `alert_webhook_delivery_logs` سیاست RLS شرکت‌محور مستقیم ندارد؛ جدول `company_id` ندارد و صرفاً از رابطه webhook استفاده می‌کند. این بخش نیازمند بازبینی امنیتی است.
6. migration فاز ۱۶ مجوز DELETE گسترده به چند جدول ذاتاً append-only می‌دهد؛ هرچند API عمومی فقط حذف import را ارائه می‌کند، سیاست retention و immutability باید دوباره کنترل شود.
7. Ruff به علت ۱۴ import نامرتب در migrationها شکست می‌خورد.
8. آزمون‌های integration نیازمند Docker در اجرای فعلی انجام نشده‌اند.
9. صفحه پروفایل شرکت فعلاً فقط اطلاعات را نمایش می‌دهد، با وجود اینکه API ویرایش شرکت وجود دارد.
10. مستند قدیمی وضعیت پیاده‌سازی فقط تا فاز ۱۴ را پوشش می‌دهد و قابلیت‌های جدید این سند را ندارد.

## ۲۳. جمع‌بندی وضعیت

هسته اصلی محصول از دریافت فایل واقعی تا تحلیل، تطبیق، یافته، شاهد، تصمیم انسانی و PDF پیاده‌سازی شده و تست واحد قابل توجهی دارد. ماژول‌های خزانه‌داری، دریافتنی، پرداختنی، هشدار و شبیه‌سازی نیز در API و رابط حاضرند. با این حال، برای اعلام production-ready شدن کل سامانه باید محدودیت‌های بخش ۲۲، به‌ویژه AI غیرفعال، fallback حافظه‌ای شبیه‌سازی، dispatcher وب‌هوک، سیاست‌های حذف/RLS و دروازه lint و integration برطرف یا رسماً پذیرفته شوند.
