# دوره مالی، دریافت فایل و آماده‌سازی پایدار

مرحله اجرایی ۲۰۲۶/۱۰/۲۵ در `didban-mali-rebuild`. کاربر فایل انتخاب می‌کند؛ بسته ساخته، فایل‌ها دریافت و مجموعه نهایی خودکار seal می‌شود. دریافت موفق فایل به معنی صحت مالی آن نیست. وضعیت «آماده تفسیر» فقط پایان اسکن و بررسی ساختار است؛ موتور مالی، تفسیر کدینگ/واحد، تطبیق و مدل هنوز متصل نیستند.

## رفتار قابل استفاده

- دوره مالی صفحه مستقل و ایجاد/نمایش/ویرایش/حذف دارد؛ ورودی شمسی به تاریخ روز میلادی بدون جابه‌جایی منطقه زمانی تبدیل می‌شود. مالک/مدیر مالی تغییر می‌دهند؛ بقیه اعضا می‌خوانند. دوره وابسته را نمی‌توان حذف کرد یا بازه/پیوند قبلی آن را عوض کرد. تغییر نام مجاز است؛ دوره قبل باید متعلق به همان شرکت و پیش از شروع دوره باشد.
- فایل Excel (`xls` و `xlsx`) و CSV پذیرفته می‌شود. هر فایل حداکثر ۲۰ MiB؛ هر بسته حداکثر ۱۰ فایل یکتا. سقف فعلی ۲۰ هزار ردیف غیرخالی مجموع فایل‌هاست و سربرگ/جمع را هم محافظه‌کارانه می‌شمارد؛ شمار ردیف مالی تا تفسیر `null` است.
- نام اصلی فقط metadata است. محتوا در کلید تصادفی خصوصی شرکت، فایل با مجوز ۶۰۰ و پوشه با مجوز ۷۰۰ ذخیره می‌شود؛ مسیر/URL عمومی دانلود نداریم. SHA256 و محتوای اصلی تغییرناپذیرند. تکرار دقیق در همان شرکت بدون ثبت دوباره شناسایی می‌شود؛ فایل ردشده بدافزاری دوباره پذیرفته نمی‌شود. تشخیص هم‌پوشانی مالی هنوز مرحله بعد است.
- فقط انتخاب نهایی فایل‌ها seal می‌شود. اگر شبکه هنگام فرمان تغییر قطع شود، تلاش عمدی بعدی همان کلید و payload را نگه می‌دارد. فایل‌های کامل‌شده پیش‌نویس حفظ می‌شوند؛ انتقال بایت‌های نیمه‌کاره ادامه‌پذیر نیست. worker فقط بسته sealشده را می‌گیرد.
- اسکن واقعی ClamAV قبل از خواندن ساختار انجام می‌شود. نبود storage/اسکنر نتیجه سالم نمی‌سازد؛ وضعیت انتظار وابستگی و تلاش محدود بعدی باقی می‌ماند. نتیجه آلوده/ساختار اساسی نامعتبر کل بسته را متوقف می‌کند. این مرحله ردیف سالم مالی جدا نمی‌کند؛ تصمیم نتیجه محدود در مرحله اعتبارسنجی مالی اجرا خواهد شد.
- CSV ابتدا UTF-8/UTF-16 دارای BOM خوانده می‌شود؛ برای کدگذاری نامشخص، سؤال ضروری بین Windows-1256 و Windows-1252 مطرح می‌شود. بستن Dialog یا خروج صفحه پاسخ نیست؛ کل بسته متوقف و سؤال پایدار می‌ماند. جواب معتبر نسخه‌دار، سابقه می‌سازد و ادامه می‌دهد. خوانده‌شدن اعلان سؤال را حل نمی‌کند.
- فقط یک دوره تعریف‌شده شرکت خودکار به بسته وصل می‌شود؛ با چند دوره، دوره بسته فعلاً خالی می‌ماند. انتخاب دوره بر اساس داده/پوشش مالی هنوز اجرا نشده و نباید از تاریخ فایل حدس قطعی زده شود.

## معماری و قرارداد

migration افزایشی `006_intake_runtime.sql` روی baseline ثابت 001–003 و 004/005 اجرا می‌شود؛ نسخه runtime اکنون ۶ است، جدول برنامه همچنان ۷۷ عدد. قرارداد کامل ۷۷ مسیر/۹۳ عملیات/۱۳۹ schema است؛ قرارداد زنده ۴۲ عملیات اجراشده را نشان می‌دهد. شناسه‌های شرکت و فایل، auth/CSRF/Origin، If-Match، fingerprint و receipt سمت سرور کنترل می‌شوند.

انتخاب مهندسی این مرحله، storage فایل خصوصی محلی و صف بادوام PostgreSQL است. این انتخاب دستور جدید کاربر یا وعده Redis/S3 نیست؛ صف خارجی برای ظرفیت فعلی اضافه نشده است. storage و دیتابیس باید در پشتیبان‌گیری هماهنگ نگهداری شوند؛ بازیابی سازمانی هنوز آزمایش نشده است.

worker با login واقعی جدا و غیرممتاز اجرا می‌شود؛ رمز مدیر migration، هویت یا secret نشست را ندارد. تنها dispatcher محدود SECURITY DEFINER شناسه کار را در سطح نصب claim می‌کند؛ خواندن/نوشتن اثرها با زمینه شرکت و RLS انجام می‌شود. HTTP اجازه claim جهانی ندارد و اتصال worker در HTTP رد می‌شود. مجوز درخواست‌کننده هر بار بازبینی می‌شود؛ سلب دسترسی، انتظار مجوز می‌سازد.

seal در یک تراکنش، policy snapshot، step و outbox را می‌نویسد. lease دارای token و انقضای ۱۲۰ ثانیه است؛ اثرها فقط با نسخه session و fence معتبر و ack همان claim در یک تراکنش commit می‌شوند. خاموشی worker کار را گم نمی‌کند؛ claim منقضی بازپس‌گیری می‌شود. worker قدیمی، لغوشده یا پاسخ مربوط به نسخه قبلی حق ثبت اثر ندارد. اسکن/خواندن خارج از تراکنش DB انجام می‌شود. پیشرفت فعلی تعداد فایل کامل‌شده است، درصد ساختگی نداریم.

خواندن XLSX بدون اجرای فرمول/ماکرو است؛ لینک خارجی، VBA، ZIP رمزشده/مسیر نامعتبر و XML ناسالم رد می‌شوند. سقف بازشدن ۶۴ MiB، ۲۰۴۸ عضو آرشیو، ۳۲ شیت، ۵۱۲ ستون و ۱۶ هزار کاراکتر هر سلول است؛ مختصات پراکنده خیلی بزرگ پیش از کتابخانه کنترل می‌شوند. XLS با xlrd و CSV با parser محدود خوانده می‌شوند. این‌ها تأیید سازگاری همه خروجی‌های بانک‌ها و نرم‌افزارها نیستند.

## نصب

از راهنمای `runtime-runbook.fa.md` برای ساخت `.env` با پنج secret و ساخت مدیر نصب استفاده کنید:

```bash
docker compose --env-file .env -f infra/compose.yaml up --build -d web
```

Compose، PostgreSQL، migration، initializer فقط-volume، API، scanner، worker و وب را اجرا می‌کند. فقط initializer برای تعیین مالکیت volume خصوصی root است؛ API/worker/web غیر root هستند. worker mount فایل‌ها را فقط می‌خواند. DB و scanner پورت host ندارند؛ وب/API روی loopback هستند. API و worker بدون اعتبارنامه migration اجرا می‌شوند.

تصویر ClamAV با digest قفل است و دیتابیس امضای همراه آن الزاماً روزآمد نیست. برای نصب سازمانی، updater امضا و دسترسی خروجی آن به سرور رسمی امضا لازم است:

```bash
docker compose --env-file .env -f infra/compose.yaml --profile signature-updates up -d scanner-updates
```

این سرویس فقط امضا دریافت می‌کند؛ فایل مالی برای اسکن از سازمان خارج نمی‌شود. در آزمون این مرحله امضای همراه تصویر استفاده شد؛ به‌روز بودن امضاهای روز ادعا نمی‌شود. نبود فایل امضا باعث عدم شروع اسکن می‌شود. حداقل منابع اولیه پیشنهادی برای پنج کاربر: Linux، ۴ هسته، ۸ GiB RAM و SSD متناسب با نگهداری فایل/backup؛ ظرفیت نهایی نیازمند بارسنجی است.

نگهداری اصل فایل خودکار پاک‌سازی نمی‌شود. حذف/بایگانی سازمانی هنوز endpoint ندارد. پس از قطع سخت برق بین نوشتن فایل و commit DB ممکن است شیء بدون ارجاع بماند؛ پاک‌سازی مدیریتی آینده باید نبود همه وابستگی‌ها را پیش از حذف ثابت کند، نه صرفاً سن فایل را.

## اعتبارسنجی و مرحله بعد

`make test-postgres18` خوشه PostgreSQL 18.6 و ClamAV مستقل موقت می‌سازد، SQL/HTTP/intake را اجرا و فقط منابع خودش را پاک می‌کند. `make test-compose-web` نصب پاک و proxy واقعی multipart بیش از ۶۴ KiB، worker خاموش/روشن، اسکن واقعی و نبود اثر تکراری را می‌آزماید. `make test-web` نوع‌ها، lint، هفت آزمون کلاینت/تاریخ و build را اجرا می‌کند. فایل‌های آزمون مصنوعی‌اند؛ فراخوانی مدل و پیام بیرونی صفر است.

گزارش‌ها: `intake-validation.json`، `postgres18-validation.json`، `compose-web-validation.json` و `intake-ui-validation.json`. بررسی دسکتاپ/موبایل در مرورگر داخلی انجام می‌شود؛ آزمون زنده Reduce Motion سیستم و بار پنج کاربر هنوز انجام نشده‌اند.

گام بعد، تفسیر نسخه‌دار و قابل استناد فایل‌ها، تعیین واحد/کدینگ/دوره و هم‌پوشانی، کنترل‌های مالی و اجرای سناریوهای مرجع با موتور تازه است. نتیجه مالی فقط با داده کافی و قواعد قطعی تولید می‌شود؛ معیارهای صحت حسابداری به مدل واگذار نمی‌شوند.

## وضعیت بعدی

مرحله تفسیر اکنون اجرا شده است؛ عبارت‌های «مرحله بعد» در این سند، وضعیت زمان آماده‌سازی را ثبت می‌کنند. وضعیت و قرارداد فعلی در [راهنمای تفسیر](interpretation-runtime.fa.md) و `interpretation-ui-validation.json` آمده است.
