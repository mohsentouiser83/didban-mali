# اجرای رابط دیدبان مالی

رابط هویت، شرکت، مجوزها، دوره، بارگذاری، تفسیر و نتایج مالی پایه به API واقعی متصل است؛ تخصیص، تطبیق‌ها، مؤدیان، پیش‌بینی، مدل و گزارش قابل دانلود باقی‌اند. رنگ، فونت و هندسه از طراحی نهایی گرفته شده‌اند؛ بازطراحی مستقلی انجام نشده است.

## نصب یکپارچه

از ریشه پروژه:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.lock
PYTHONPATH=apps/api .venv/bin/python -m didban.manage init-env
docker compose --env-file .env -f infra/compose.yaml up --build -d web
```

اگر `.env` از مرحله API دارید، ابزار آن را بازنویسی نمی‌کند. `DIDBAN_PUBLIC_ORIGIN=http://127.0.0.1:18148` و `DIDBAN_WEB_PORT=18148` را برای اجرای محلی وب تعیین کنید؛ پورت API مستقل 18147 است. برای استقرار سازمانی، origin واقعی HTTPS و cookie امن الزامی است؛ استقرار سازمانی در این مرحله انجام نشده است.

ساخت اولین مدیر با فرمان تعاملی [راهنمای API](runtime-runbook.fa.md) انجام می‌شود. رمز پیش‌فرض یا ثبت‌نام عمومی وجود ندارد. سپس نشانی `http://127.0.0.1:18148/login` را باز کنید. image وب غیر root، با فایل‌سیستم فقط‌خواندنی و بدون رمز DB/مدیر اجرا می‌شود. سرور API و پایگاه داده مرزهای دسترسی مستقل خود را دارند.

## ترتیب کار

۱. مدیر نصب با ایمیل/رمز وارد می‌شود؛ در «کاربران سازمان» حساب می‌سازد و کد دعوت را دستی و خصوصی تحویل می‌دهد. کد در URL، localStorage یا اعلان ذخیره نمی‌شود. بستن پنجره حین درخواست متوقف است تا پاسخ کد گم نشود. دعوت دوباره برای حساب فعال‌نشده، کدهای دعوت قبلی را باطل می‌کند.
۲. کاربر از صفحه «فعال‌سازی دعوت» رمز تعیین می‌کند و سپس جداگانه وارد می‌شود. مدیر برای حساب فعال، کد بازیابی رمز صادر می‌کند. مصرف موفق کد، همه نشست‌های قبلی را لغو می‌کند. پیام بیرونی ارسال نمی‌شود.
۳. مدیر نصب شرکت و مالک اولیه را انتخاب می‌کند. ایجاد شرکت به‌تنهایی به مدیر نصب عضویت مالی نمی‌دهد؛ فهرست شرکت‌ها فقط عضویت‌های مجاز او را نشان می‌دهد.
۴. مالک از «اعضا و مجوزها» کاربر موجود را با ایمیل اضافه می‌کند؛ نقش و فعال‌بودن عضویت نسخه‌دارند. نام/ایمیل اعضا صرفاً پس از کنترل مالک همان شرکت خوانده می‌شود. فهرست عمومی کاربران برای مالک وجود ندارد؛ فهرست کل نصب فقط برای مدیر نصب است.
۵. مدیر مالی اختیار پیش‌فرض تأیید گزارش دارد. مالک/مشاور از مسیر «مجوز تأیید» به grant صریح نیاز دارند؛ فقط مالک می‌تواند با دلیل ثبت‌شده اعطا/لغو کند. کاهش نقش یا غیرفعال‌سازی، مجوز صریح قبلی را لغو می‌کند. تغییر آخرین مالک رد می‌شود. این صفحه خودِ گزارش مالی را تأیید نمی‌کند.
۶. تنظیم نام، ریال/تومان نمایشی و بایگانی/بازگردانی شرکت در صفحه مستقل تنظیمات است. بایگانی داده را حذف نمی‌کند. تعارض نسخه به کاربر نشان داده می‌شود؛ دریافت نسخه تازه تصمیمی صریح است و درخواست با نسخه جدید ساکت تکرار نمی‌شود.

## اجرای محلی و بررسی

Node 22 برای ساخت آزموده شده است. از ریشه:

```bash
npm ci
npm run generate:api
npm run typecheck
npm run lint
npm run test:client
npm run build
DIDBAN_API_ORIGIN=http://127.0.0.1:18147 npm start
```

API باید origin وب را مجاز بداند. `DIDBAN_API_ORIGIN` یک تنظیم صرفاً سروری است و به مرورگر داده نمی‌شود. cookieها HttpOnly باقی می‌مانند؛ وب هدرهای CSRF، کلید تکرار و نسخه را به API می‌رساند. proxy تغییرمسیر خارجی را دنبال نمی‌کند، بدنه را محدود می‌کند و خطای ارتباط را بدون جزئیات داخلی نشان می‌دهد. IP واقعی کاربر پشت proxy هنوز تفکیک نمی‌شود؛ محدودیت IP سمت API در این نصب مشترک است و محدودیت مستقل هر هویت همچنان برقرار است.

```bash
make test-postgres18
make test-compose-web
make check
```

`test-compose-web` نصب پاک DB/API/وب، اجرای غیر root، cookie و CSRF از proxy هم‌مبدأ، ورود، شرکت، تکرار migration و خروج را در پروژه تصادفی Docker بررسی می‌کند و فقط همان منابع را پاک می‌کند. این آزمون HTTP جای آزمون مرورگر نیست.

برای بازبینی دستی مصنوعی می‌توان ` .venv/bin/python tools/ui_test_environment.py start` را اجرا کرد؛ فقط DB تازه، حساب‌های `ui.*@fixture.invalid` و رمز آزمون `UiValidation-Only-426!` می‌سازد. این حساب‌ها بخشی از محصول یا نصب واقعی نیستند. وب 18148 و API 18149 روی loopback اجرا می‌شوند. اگر محیط آزمون باز باشد، دوباره ساخته نمی‌شود. فرمان `stop` همان محیط را متوقف و container مصنوعی آن را حذف می‌کند. اطلاعات نگهداری محیط در `.local/ui-validation` خصوصی و خارج از Git است.

## دامنه پذیرش

[گزارش بررسی مرورگر](ui-validation.json) وضعیت واقعی هر بررسی را ثبت می‌کند. دسکتاپ و موبایل در مرورگر داخلی Codex و صفحات ورود، شرکت‌ها، تنظیمات، اعضا و کاربران بررسی شده‌اند. فعال‌سازی/بازیابی موفق رمز در آزمون HTTP پوشش دارد؛ در مرورگر تغییر واقعی رمز انجام نشده است. محافظ‌های کاهش حرکت در source/CSS وجود دارند؛ آزمون زنده با تنظیم سیستم روی Reduce Motion هنوز تأیید نشده و نباید به‌عنوان قبولی آن گزارش شود.

پذیرش کامل موتور مالی، انتشار عمومی، بارسنجی، نصب سازمانی/TLS، backup/restore و تأیید حسابدار همچنان باقی‌اند.

برای شبکه‌هایی که دریافت بسته‌های npm کند است، `NPM_REGISTRY` در تنظیم ساخت وب قابل تغییر است؛ پیش‌فرض registry رسمی است. دریافت‌ها timeout و retry محدود و cache ساخت دارند و integrity قفل npm کنترل می‌شود. در بررسی این محیط از mirror عمومی `https://registry.npmmirror.com` استفاده شد؛ مقدار `DIDBAN_TEST_NPM_REGISTRY` فقط برای ابزار آزمون نصب است.

## افزوده مرحله آماده‌سازی

دوره‌ها در `/companies/{id}/periods`، بارگذاری در `/companies/{id}/uploads` و هر پرونده در `/companies/{id}/uploads/{session}` قرار دارد. مالک/مدیر مالی دوره را مدیریت می‌کنند؛ مشاور نیز بارگذاری و پاسخ سؤال را انجام می‌دهد؛ مشاهده‌گر فقط می‌خواند. تقویم شمسی مشترک، ورود دستی تاریخ، فرم و focus خطا مشترک‌اند.

انتخاب فایل به ساخت بسته، انتقال سریالی با کلیدهای پایدار و seal خودکار منتهی می‌شود. اگر انتقال قطع شود، فایل‌های کامل‌شده در پیش‌نویس محفوظ‌اند؛ در پرونده، فایل‌های باقی‌مانده را انتخاب کنید یا آماده‌سازی همین فایل‌ها را ادامه دهید. انتقال نیمه‌کاره مرورگر خودکار از بایت میانی ادامه پیدا نمی‌کند. پردازش sealشده مستقل از بازبودن مرورگر ادامه می‌یابد؛ سؤال ضروری کل بسته را روی سرور متوقف می‌کند.

بازبینی جدید در `intake-ui-validation.json` ثبت می‌شود؛ گزارش `ui-validation.json` مربوط به مرحله قبلی هویت است. محیط مرورگر برای اسکن نیاز به ClamAV محلی دارد؛ `DIDBAN_TEST_SCANNER_PORT` هنگام start به worker داده می‌شود (پیش‌فرض 3310). فرمان stop فقط scanner ثبت‌شده به‌عنوان متعلق به همین محیط آزمایشی را حذف می‌کند؛ scanner مستقل بیرونی حذف نمی‌شود. نصب کامل Compose این وابستگی را خودش راه‌اندازی می‌کند.

## مرحله تفسیر ورودی — ۲۰۲۶/۱۰/۲۵

runtime نسخه ۷ با migration افزایشی 007، شامل ۷۹ جدول برنامه و ۴۶ عملیات فعال است؛ قرارداد کامل ۸۰ مسیر، ۹۷ عملیات و ۱۵۲ schema دارد. تفسیر کنترل‌شده، داده استاندارد تغییرناپذیر، اصلاح نسخه‌دار تنظیمات، سؤال‌های ضروری و شواهد ردیف اجرا شده‌اند. مرجع فعلی [راهنمای تفسیر](interpretation-runtime.fa.md) و گزارش‌های جدید اعتبارسنجی است؛ وضعیت آماده‌سازیِ صرف در بخش‌های قبلی تاریخی است.

`interpretation_finished_at` آماده‌بودن داده برای بررسی است، نه پایان محاسبات مالی. این مرحله manifest مالی، شاخص، ثبت دفتر، تخصیص یا فراخوانی مدل نمی‌سازد. قالب ناشناخته به نگاشت صریح می‌رسد؛ اظهار پوشش جای کنترل مستقل نیست. نسخه‌های قبلی و actor واقعی تصمیم‌ها حفظ شوند. گام بعد، محاسبه قطعی و فعال‌سازی dataset/manifest با جلوگیری از اثر دوباره منابع است.

## وضعیت جاری موج سوم — ۲۰۲۶/۱۰/۲۶

این بخش بر وضعیت‌های تاریخی پیشین مقدم است. runtime۱۰ با migrationهای ۰۰۱–۰۱۷، ۹۴ جدول برنامه و ۱۰۴ عملیات ثبت‌شده HTTP اجرا می‌شود؛ قرارداد کامل ۹۸ مسیر، ۱۱۹ عملیات و ۱۷۸ schema دارد. ثبت endpoint به‌تنهایی آزمون کامل آن نیست.

گزارش ثابت پس از تحلیل، نسخه دقیق manifest، تطبیق‌ها، تسویه، نقدینگی، پیش‌بینی و شواهد را نگه می‌دارد و سه کار بادوام PDF، Excel و CSV خطا می‌سازد. `analysis_finished_at` پایان تحلیل است؛ پایان نوبت فقط پس از آماده‌شدن هر سه خروجی و رفع مانع سؤال ثبت می‌شود. `report_id` روی نوبت و لینک همان گزارش در رابط موجود است. تأیید با مجوز جاری و همان نسخه ثبت می‌شود و به نسخه تازه منتقل نمی‌شود. نوبت تمام‌شده دوباره باز نمی‌شود؛ بازبینی پیش‌بینی نوبت ادامه مستقل دارد.

صفحات مستقل گزارش‌ها، سیاست‌ها و اصل فایل متصل‌اند. سقف بارگذاری و فرض پیشنهادی پیش‌بینی نسخه‌دار و مصرف می‌شوند؛ بایگانی اثر مالی و شواهد را حفظ می‌کند. مدت نگهداری بدون پاک‌سازی خودکار است؛ حذف قطعی تنها برای اصل واقعاً فاقد وابستگی، با مجوز و پاک‌سازی فیزیکی بادوام انجام می‌شود. جزئیات در `reports-runtime.fa.md` و `policy-retention-runtime.fa.md` است.

پشتیبان رمز‌شده، تنظیمات HTTPS و بازیابی در مقصد تازه در `installation-readiness.fa.md` شرح داده شده‌اند. آزمون بازیابی برنامه فعلی روی دو PostgreSQL مستقل، مدرک نصب پاک Compose نیست. `capacity-validation.json` وضعیت واقعی آخرین اندازه‌گیری را نشان می‌دهد؛ پنج استفاده‌کننده در یک بسته بانکی مصنوعی به معنی پنج تحلیل سنگین هم‌زمان نیست. ساخت تازه و نصب مستقل Compose با ۱۵ کنترل، شامل فونت PDF و نوشتن خروجی توسط worker، موفق شد؛ HTTPS و بازیابی کامل روی سرور سازمان هنوز بررسی نشده است.

گزارش‌های `reports-validation.json`، `report-rendering-validation.json`، `policy-validation.json`، `delivery-workflow-validation.json`، `backup-bundle-validation.json`، `installation-config-validation.json` و `restore-validation.json` شواهد این مرحله‌اند. ظرفیت کامل و بازیابی با ۱۷migration موفق‌اند؛ اجرای نهایی یکپارچه و حالت‌های باقی‌مانده مرورگر در حال به‌روزرسانی‌اند؛ وضعیت pass/fail و hash هر گزارش مرجع همان دامنه است. `wave2-validation.json` و گزارش‌های نصب مراحل قبل، شاهد نسخه فعلی همه قابلیت‌ها نیستند. مدل زنده و provider برای تشخیص فایل/نگاشت/نقش حساب، ارزیابی قالب‌های متنوع، کاهش حرکت واقعی سیستم‌عامل و پذیرش مالی/سازمانی همچنان باقی‌اند. هیچ پیام بیرونی، نصب روی سازمان یا فراخوانی مدل زنده انجام نشده است.
