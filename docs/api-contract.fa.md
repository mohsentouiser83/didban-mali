# قرارداد API ساخت تازه — ۰٫۱

افزونه ۲۰۲۶/۱۰/۲۹ شامل شش عملیات ماژول/مجوز/سابقه، شش عملیات بازبینی ورودی، شش عملیات تحلیل/پیگیری/خلاصه و ۲۵ عملیات حقوق است. مرجع دقیق مسیرها و schemaها `contracts/openapi.json` تولیدشده است؛ ثبت مسیر به معنی پذیرش قانونی یا استقرار آن نیست. قراردادهای اجرا: [ماژول‌ها](extension-foundation-runtime.fa.md)، [بازبینی](input-review-runtime.fa.md)، [تحلیل](actionable-analysis-runtime.fa.md) و [حقوق](payroll-runtime.fa.md).

## تشخیص مجدد خودکار ورودی — ۲۰۲۶/۱۰/۲۶

مسیر موجود POST /companies/{company_id}/processing-sessions/{session_id}/interpret علاوه بر شروع اولیه، درخواست صریح تشخیص مجدد برای بسته دارای سؤال بازِ interpretation_mapping یا interpretation_kind را می‌پذیرد. مجوز company.operate، نسخه و کلید تکرارپذیری الزامی‌اند. بسته منتشرشده، کامل، لغوشده یا دارای نتیجه مالی قابل بازگشایی نیست. فقط سؤال‌های نگاشت/نوعِ فایل‌های مربوط supersede می‌شوند؛ پاسخ ساختگی ایجاد نمی‌شود، تنظیم انسانی و نسخه‌های پیشین باقی می‌مانند و سایر سؤال‌های ضروری همچنان مانع worker هستند. اگر ابهام تکرار شود، سؤال تازه ساخته می‌شود. درخواست با رویداد interpretation.automatic_retry_requested ممیزی و با نوع عملیات موجود start_interpretation ثبت می‌شود؛ نیازی به تغییر schema نیست.

مرجع ماشین‌خوان `contracts/openapi.json` با OpenAPI 3.1.1 از `tools/build_openapi.py` تولید می‌شود. در مرحله فعلی، registry سرور ۱۵۲ عملیات فعال دارد؛ قرارداد کامل ۱۳۷ مسیر، ۱۶۷ عملیات و ۲۵۵ schema را شامل می‌شود. `/openapi.json` سرویس فقط مسیرهای فعال را ارائه می‌کند. شمارهای قدیمی مربوط به مراحل قبلی‌اند. مرجع معنا [مشخصات رسمی OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html) است.

## قواعد مشترک

- همه مسیرهای مالی زیر `/api/v1/companies/{company_id}` هستند. شناسه‌ها UUID؛ شناسه منبع مثل شماره فاکتور متن جداست. شرکت و actor از مسیر مجاز و نشست معتبر استخراج شوند؛ در body mutation فیلد actor/company پذیرفته نشود.
- نشست cookie امن HttpOnly/Secure/SameSite است. گرفتن CSRF token برای نشست ناشناس یا معتبر مجاز است؛ token مجوز مالی نیست. mutationها `X-CSRF-Token` و `Idempotency-Key` دارند. ورود، دعوت و reset ثبت‌نام عمومی نیستند. bootstrap مالک نصب فقط در CLI نصب آینده انجام شود.
- مبلغ JSON رشته Decimal با رقم لاتین و واحد IRR است؛ null داده ناموجود است. API float، NaN، Infinity، ارز خارجی در داده مالی یا دقت بیشتر از قرارداد را نپذیرد. تبدیل نمایش تومان سمت UI محاسبه منبع را عوض نمی‌کند.
- request/responseهای شیء بسته‌اند: `additionalProperties:false`. پاسخ سؤال `oneOf` نوع‌دار است: واحد، تاریخ، گزینه، پوشش، نقش حساب، ارتباط بانک/دفتر یا نامعلومِ مجاز. علاوه بر schema، قید همان سؤال و شرکت/نسخه اعتبارسنجی شود.
- فهرست‌ها cursor و limit حداکثر ۱۰۰ دارند. ترتیب `(created_at,id)`، فیلتر ثابت، شرکت و endpoint در cursor امضاشده مقید شوند. تغییر فیلتر cursor را نامعتبر کند. جدول‌های موجود در manifest از انتخاب ثابت خوانده شوند؛ صرف cursor برای snapshot زنده تضمین یکسان‌بودن داده نیست.
- `If-Match: "v12"` در تغییر نسخه‌دار الزامی است؛ نبود پیش‌شرط ۴۲۸ و نسخه نامعتبر ۴۰۹ است. نسخه پاسخ در ETag و فیلد version/session_version قرار می‌گیرد. برای پاسخ سؤال، **نسخه فعلی session** ملاک است، نه نسخه زمان ایجاد سؤال. برای تغییر نقش حساب/ارتباط بانک، نسخه resource حساب/بانک مقایسه شود.

## دسترسی و تصمیم‌ها

`company.read` نیازمند عضویت فعال است؛ مدیر نصب بدون عضویت مستثنا نیست. `company.operate` برای مالک، مدیر مالی و مشاور/حسابدار در شرکت مجاز است؛ D04 اختیار عملیاتی مشاور را نهایی کرده است. مشاهده‌گر mutation مالی ندارد، اما سؤال دستیار فقط‌خواندنی و خوانده‌شدن اعلان شخصی mutation عملیاتی مالی نیستند.

`company.approve_report` مطابق D05 برای مدیر مالی یا مالک/مشاورِ دارای مجوز صریح همان شرکت است. `company.owner` در مسیر اعطا/لغو این مجوز الزام قطعی D08 است. مجوز تنظیم سیاست و سایر خانه‌های غیرصریح ماتریس، پیش‌فرض مهندسی مستند قرارداد پایه‌اند؛ به‌عنوان تصمیم صریح کاربر معرفی نشوند.

نمای مجوز صریح، در نبود اعطای قبلی disabled است. ETag این endpoint از نسخه عضویت گرفته شود: نخستین PUT نیز عضویت را قفل، If-Match را کنترل و نسخه را افزایش دهد؛ رکورد grant و permission_event در همان تراکنش ثبت شوند. نقش مالی مجوز اعطا ندارد. مالک برای تأیید خودش هم عمل اعطای صریح ثبت می‌کند؛ مالکیت به‌تنهایی تأیید نیست.

## تکرار، خطا و دانلود

کلید تکرار در دامنه `(company,actor,route,key)` با hash کانونیکال payload ثبت شود. برای upload hash بایت فایل نیز جزو payload است؛ نام فایل به‌تنهایی کافی نیست. کلید و payload یکسان همان نتیجه را بدهند؛ payload متفاوت ۴۰۹. پاسخ mutation و اثر دامنه همراه outbox در یک commit ثبت شوند. نسخه قدیمی به معنی retry با کلید تازه برای دورزدن تعارض نیست. هویت/نصب، idempotency را در مرز ممتاز و بدون فرض company_id مدیریت کنند.

در زیرمجموعه اجرایی، hash درخواست HMAC است تا محتوای رمز از hash قابل حدس سریع نباشد. رسیدهای هویت شامل cookie/token با Fernet رمز می‌شوند؛ token خام در DB ذخیره نمی‌شود. receipt فرمان شرکتی پیش از اثر ایجاد و با اثر اتمی تکمیل می‌شود؛ در لغو عضویت خودِ مالک نیز فقط همان receipt قبلاً مجاز قابل تکمیل است، نه دسترسی بعدی به شرکت. احراز هویت/مجوز جاری بر replay مقدم است؛ کلید ورود قبلی نشست لغوشده را زنده نمی‌کند.

`Error` همیشه code، message_fa، request_id، retryable، field_errors و details نوع‌دار دارد. نگاشت اصلی: ۴۰۱ بدون نشست، ۴۰۳ نقش ناکافی، ۴۰۴ منبع غایب/غیرقابل دسترس، ۴۰۹ تضاد نسخه/ظرفیت/وابستگی، ۴۱۳ سقف، ۴۱۵ فرمت، ۴۲۲ محتوای نامعتبر و ۵۰۳ وابستگی موقت. SQLSTATE توسط application service به خطای عمومی نگاشت شود؛ stacktrace، SQL، متن provider و secret به مرورگر نروند.

زیرمجموعه ورود همچنین ۴۲۹ برای محدودیت تلاش و ۵۰۰ عمومی بدون جزئیات داخلی دارد. خطاهای ۴۰۴/۴۰۵ نیز قالب یکسان Error دارند. JSON تکراری، متن NUL یا Unicode نامعتبر و درخواست بیشتر از سقف پیش از تغییر داده رد می‌شوند. گزارش منتشرنشده در API قابل خواندن/تأیید نیست.

خروجی async ابتدا job/operation ID می‌دهد؛ وضعیت از مسیر مشخص بازیابی می‌شود. دانلود export فقط پس از ready و کنترل دوباره عضویت، scope و دسترسی همان manifest مجاز است. object_key، مسیر دیسک و URL عمومی دائمی در schema عمومی وجود ندارد. خطا و فایل CSV از formula injection محافظت شوند؛ اصل خام در شاهد باقی بماند.

## سازگاری با نمونه‌ها

`contracts/examples` نمونه wire معتبر و نمونه عمداً نامعتبر دارد. مقادیر مالی مثبت از golden مستقل در `docs/validation/rebuild-v1/expected/baseline.json` گرفته شده‌اند. aliasهای خوانا برای API به UUID نگاشت می‌شوند. fixtureهای اولیه انتظار مالی‌اند؛ ساختار ساده قدیمی MetricObservation عین schema نهایی جدید نیست. نگاشت در `tools/check_contracts.py` صریح است و عدد طلایی بازنویسی نمی‌شود.

بررسی ساختار OpenAPI و مثال‌ها همچنان مستقل است. اکنون آزمون واقعی HTTP/DB برای ورود، CSRF، cursor، عضویت، نسخه و مجوز و آزمون TCP در نصب Docker اجرا می‌شود. parser/streaming فایل، حوزه مالی دیگر هنوز به آزمون آینده نیاز دارند؛ این نتیجه کل T01–T14 نیست.

## تکمیل قرارداد برای رابط سازمان

- `GET /api/v1/admin/users` فهرست cursorدار نام/ایمیل، مدیریت نصب و وضعیت فعال‌سازی/غیرفعال‌سازی را فقط برای مدیر نصب می‌دهد؛ password hash، token و اطلاعات نشست برنمی‌گرداند. cursor آن به actor و resource مستقل users مقید است.
- `POST /api/v1/admin/users/{user_id}/invitation` فقط برای کاربر فعال‌نشده و مدیر نصب است؛ کدهای قبلی همان نوع را باطل می‌کند و کد تازه دستی برمی‌گرداند. حساب فعال از مسیر reset استفاده می‌کند.
- `MembershipCreate` دقیقاً یکی از `user_id` یا `email` را همراه نقش می‌پذیرد؛ مقدارهای هم‌زمان رد می‌شوند. ایمیل فقط lookup دقیق حساب موجود است؛ مالک نمی‌تواند حساب سراسری جدید بسازد.
- فهرست عضویت از `MemberDirectoryEntry` با نام/ایمیل استفاده می‌کند. service نخست مالک و شرکت را کنترل می‌کند، سپس صرفاً پروفایل شناسه‌های همان فهرست مجاز را از مرز هویت می‌خواند؛ فهرست global برای مالک باز نشده است.
- تعداد عملیات زنده اکنون ۲۳ است؛ قرارداد کامل ۹۳ عملیات دارد و حوزه‌های مالی آینده را نیز توصیف می‌کند. کلاینت وب و نوع‌های TypeScript از این قرارداد تولید شده‌اند؛ آزمون مرورگر در گزارش مستقل UI آمده است.

## افزوده مرحله آماده‌سازی — ۲۰۲۶/۱۰/۲۵

قرارداد کامل اکنون ۱۳۹ schema دارد (۷۷ مسیر/۹۳ عملیات). قرارداد زنده ۴۲ عملیات ساخته‌شده، شامل دوره مالی و آماده‌سازی، را ارائه می‌کند. uploadFile فقط یک multipart field به نام file با سقف ۲۰ MiB می‌گیرد؛ پاسخ ۲۰۲ دریافت فایل است و نتیجه مالی نیست. seal با شناسه دقیق همه فایل‌ها، If-Match و کلید تکرار انجام می‌شود. جزئیات در `intake-runtime.fa.md` است.

## مرحله تفسیر ورودی — ۲۰۲۶/۱۰/۲۵

runtime نسخه ۷ با migration افزایشی 007، شامل ۷۹ جدول برنامه و ۴۶ عملیات فعال است؛ قرارداد کامل ۸۰ مسیر، ۹۷ عملیات و ۱۵۲ schema دارد. تفسیر کنترل‌شده، داده استاندارد تغییرناپذیر، اصلاح نسخه‌دار تنظیمات، سؤال‌های ضروری و شواهد ردیف اجرا شده‌اند. مرجع فعلی [راهنمای تفسیر](interpretation-runtime.fa.md) و گزارش‌های جدید اعتبارسنجی است؛ وضعیت آماده‌سازیِ صرف در بخش‌های قبلی تاریخی است.

`interpretation_finished_at` آماده‌بودن داده برای بررسی است، نه پایان محاسبات مالی. این مرحله manifest مالی، شاخص، ثبت دفتر، تخصیص یا فراخوانی مدل نمی‌سازد. قالب ناشناخته به نگاشت صریح می‌رسد؛ اظهار پوشش جای کنترل مستقل نیست. نسخه‌های قبلی و actor واقعی تصمیم‌ها حفظ شوند. گام بعد، محاسبه قطعی و فعال‌سازی dataset/manifest با جلوگیری از اثر دوباره منابع است.

## وضعیت جاری موج سوم — ۲۰۲۶/۱۰/۲۶

این بخش بر وضعیت‌های تاریخی پیشین مقدم است. runtime۱۰ با migrationهای ۰۰۱–۰۱۷، ۹۴ جدول برنامه و ۱۰۴ عملیات ثبت‌شده HTTP اجرا می‌شود؛ قرارداد کامل ۹۸ مسیر، ۱۱۹ عملیات و ۱۷۸ schema دارد. ثبت endpoint به‌تنهایی آزمون کامل آن نیست.

گزارش ثابت پس از تحلیل، نسخه دقیق manifest، تطبیق‌ها، تسویه، نقدینگی، پیش‌بینی و شواهد را نگه می‌دارد و سه کار بادوام PDF، Excel و CSV خطا می‌سازد. `analysis_finished_at` پایان تحلیل است؛ پایان نوبت فقط پس از آماده‌شدن هر سه خروجی و رفع مانع سؤال ثبت می‌شود. `report_id` روی نوبت و لینک همان گزارش در رابط موجود است. تأیید با مجوز جاری و همان نسخه ثبت می‌شود و به نسخه تازه منتقل نمی‌شود. نوبت تمام‌شده دوباره باز نمی‌شود؛ بازبینی پیش‌بینی نوبت ادامه مستقل دارد.

صفحات مستقل گزارش‌ها، سیاست‌ها و اصل فایل متصل‌اند. سقف بارگذاری و فرض پیشنهادی پیش‌بینی نسخه‌دار و مصرف می‌شوند؛ بایگانی اثر مالی و شواهد را حفظ می‌کند. مدت نگهداری بدون پاک‌سازی خودکار است؛ حذف قطعی تنها برای اصل واقعاً فاقد وابستگی، با مجوز و پاک‌سازی فیزیکی بادوام انجام می‌شود. جزئیات در `reports-runtime.fa.md` و `policy-retention-runtime.fa.md` است.

پشتیبان رمز‌شده، تنظیمات HTTPS و بازیابی در مقصد تازه در `installation-readiness.fa.md` شرح داده شده‌اند. آزمون بازیابی برنامه فعلی روی دو PostgreSQL مستقل، مدرک نصب پاک Compose نیست. `capacity-validation.json` وضعیت واقعی آخرین اندازه‌گیری را نشان می‌دهد؛ پنج استفاده‌کننده در یک بسته بانکی مصنوعی به معنی پنج تحلیل سنگین هم‌زمان نیست. ساخت image پاک به اختلال دریافت بسته‌ها متوقف شده و TLS واقعی سازمان هنوز بررسی نشده است.

گزارش‌های `reports-validation.json`، `report-rendering-validation.json`، `policy-validation.json`، `delivery-workflow-validation.json`، `backup-bundle-validation.json`، `installation-config-validation.json` و `restore-validation.json` شواهد این مرحله‌اند. ظرفیت کامل و بازیابی با ۱۷migration موفق‌اند؛ اجرای نهایی یکپارچه و حالت‌های باقی‌مانده مرورگر در حال به‌روزرسانی‌اند؛ وضعیت pass/fail و hash هر گزارش مرجع همان دامنه است. `wave2-validation.json` و گزارش‌های نصب مراحل قبل، شاهد نسخه فعلی همه قابلیت‌ها نیستند. مدل زنده و provider برای تشخیص فایل/نگاشت/نقش حساب، ارزیابی قالب‌های متنوع، کاهش حرکت واقعی سیستم‌عامل و پذیرش مالی/سازمانی همچنان باقی‌اند. هیچ پیام بیرونی، نصب روی سازمان یا فراخوانی مدل زنده انجام نشده است.

عملیات افزوده گزارش: `listReports`، `generateReport`، `createExport`، `getExport`، `downloadExport` و `retryExport`؛ `getReport` و `approveReport` اکنون گزارش تولیدشده نسخه‌دار را مصرف می‌کنند. دانلود برخلاف پاسخ JSON، بایت PDF/XLSX/CSV با media type قراردادی، نام attachment کنترل‌شده و `nosniff` دارد؛ هر دانلود مجوز جاری، اندازه و hash را بررسی می‌کند. عملیات سیاست/منبع: `listPolicies`، `createPolicyVersion`، `getUploadPolicy`، `listSourceFiles`، `getSourceDeletionImpact`، `archiveSourceFile`، `deleteSourceFile`، `getRetentionPolicy` و `updateRetentionPolicy`. شناسه `report_id`، نوع نوبت `purpose` و `source_session_id` در قرارداد نوبت به UI کمک می‌کنند نسخه و ادامه پیش‌بینی را درست نشان دهد.

## گزارش‌های مدیر مالی — ۲۰۲۶/۱۰/۲۶

مسیرهای تازه شامل `POST /results/{manifest_id}/management-reports`، `GET /reports/{report_id}/management`، `GET /reports/{report_id}/statement-template`، `POST /statement-templates/parse` و `GET /statement-templates/example` هستند. مسیرها همچنان زیر شرکت مجاز قرار دارند؛ تولید/خواندن قالب ورودی مجوز عملیاتی و مشاهده/دانلود مجوز خواندن می‌خواهد. بارگذاری قالب متن‌محور و محدود از محتوای مالی جداست. قرارداد دقیق در OpenAPI تولیدشده و [راهنمای گزارش مدیریتی](management-reports-runtime.fa.md) آمده است. تاریخ خروجی گزارش سفارشی و شاخص‌های خلاصه آن از بازه انتخابی‌اند؛ manifest منبع بازنویسی نمی‌شود.


## ادامه گزارش‌های مدیریتی — ۲۰۲۶/۱۰/۲۶

تراز آزمایشی شش‌ستونی مستقل، دامنه و وضعیت اختتامیه صریح، و صورت جریان وجوه نقد دفتری در مسیر جدا اضافه شدند. قرارداد، کنترل‌ها و محدودیت‌های جاری در [تکمیل صورت‌های مالی](statements-v2-runtime.fa.md) ثبت شده‌اند. Migration افزایشی ۰۲۳ و فرمول `management-v2.0` مرجع این توسعه‌اند؛ وضعیت و محدودیت‌های تاریخی بالا دلیل پذیرش مالی یا نصب سازمانی نیستند.
