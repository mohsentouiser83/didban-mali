# نصب سازمانی، پشتیبان و بازیابی

به‌روزرسانی اعتبارسنجی: ۲۰۲۶/۱۰/۲۶. این راهنما برای مخزن تازه است. اجرای موفق آزمون محلی، نصب روی سرور سازمان یا تأیید حسابدار نیست. هیچ نصب بیرونی، تغییر DNS یا ارسال پیام انجام نشده است.

## وضعیت فعلی

- تنظیمات Compose خصوصی، جداسازی اتصال‌های هویت/مالی/worker، ریشه فقط‌خواندنی و دسترسی غیر root برقرار است. worker فقط برای نوشتن خروجی‌های خصوصی به volume داده دسترسی نوشتن دارد؛ ریشه کانتینر فقط‌خواندنی است. فونت‌های PDF در image کپی و وابستگی‌های تولید گزارش قفل شدند.
- ابزار پشتیبان رمز‌شده و بازیابی در مقصد تازه نوشته شد. ۹ آزمون رمزنگاری/خرابی/مسیر/امتناع از حذف مقصد موجود/بازگشت سرویس پس از خطا و ۵ آزمون تنظیمات امنیتی موفق‌اند؛ مرجع `backup-bundle-validation.json` و `installation-config-validation.json` است.
- `restore-validation.json` بازیابی واقعی روی دو PostgreSQL 18 مستقل را ثبت می‌کند: برنامه فعلی روی میزبان، شش فایل اصلی و سه خروجی واقعی تولیدشده، تأیید گزارش و بایگانی منبع؛ تعداد رکوردها، hash مهاجرت‌ها، فایل‌ها، مجوزهای شرکت و بایت خروجی‌ها پس از بازیابی بررسی شده‌اند. این آزمون از توابع مشترک archive/encryption/recovery استفاده می‌کند؛ آزمون نصب پاک image/Compose نیست.
- ساخت تازه image و نصب مستقل Compose در ۲۰۲۶/۱۰/۲۶ موفق شدند: ۱۵ کنترل، شامل ورود از proxy وب، ClamAV واقعی، restart، فونت تعبیه‌شده PDF و نوشتن خروجی توسط worker غیر root. خطاهای قبلی DNS/دریافت بسته‌ها تاریخی‌اند؛ تنظیم DNS و اعتبارسنجی TLS تغییر نکردند. دامنه آزمون نصب، smoke و ورودی است؛ بازیابی کامل همین Compose روی سرور سازمان ادعا نمی‌شود.
- TLS در قالب آماده شده است؛ گواهی سازمان، اعتماد زنجیره، HTTPS واقعی و دسترسی شبکه سازمان هنوز باید روی سرور مقصد بررسی شوند.

## نصب با HTTPS

۱. فایل محرمانه تنظیمات را با CLI `didban.manage init-env` بسازید؛ مجوز آن ۶۰۰ بماند. رمزهای چهار مرز و `DIDBAN_SECRET` جدا و پایدار هستند. این secret برای خواندن رسیدهای رمز‌شده نیز لازم است و با restart عوض نمی‌شود.

۲. `DIDBAN_PUBLIC_ORIGIN` را برابر دامنه دقیق HTTPS سازمان قرار دهید. مدل می‌تواند خالی بماند. API و وب روی loopback بمانند؛ پورت PostgreSQL منتشر نشود. تنظیمات سازمانی را با دو فایل Compose اجرا کنید:

```bash
docker compose -p didban-organization --env-file .env \
  -f infra/compose.yaml -f infra/compose.production.yaml config --quiet
.venv/bin/python tools/check_installation_config.py \
  --project didban-organization --env-file .env
```

اعتبارسنج تنظیمات، پیکربندی پایه را می‌خواند؛ مقدار `DIDBAN_COOKIE_SECURE=true` را در خود فایل `.env` نیز ثبت کنید تا ابزار و override یکسان باشند. این ابزار مقدار secretها را چاپ نمی‌کند. URL دقیق، cookie امن، جداسازی رمزها، پورت‌های loopback، ریشه فقط‌خواندنی و نبود secret مالی در وب را کنترل می‌کند؛ handshake و اعتماد گواهی را ثابت نمی‌کند.

۳. قالب `infra/tls/nginx.conf.example` را با دامنه و مسیر گواهی واقعی تطبیق دهید. گواهی/کلید متعلق به سازمان و reverse proxy باید جداگانه مدیریت و پشتیبان‌گیری شوند. ابتدا پیکربندی Nginx و اعتبار/انقضای گواهی را بررسی کنید؛ سپس با HTTPS ورود، cookie امن، بارگذاری و دانلود را از شبکه مجاز سازمان آزمایش کنید. HSTS فقط پس از تأیید دامنه و HTTPS فعال شود. در این کار هیچ سرویس عمومی TLS فعال نشده است.

۴. نصب پاک، migration، شروع سرویس‌ها و اسکنر واقعی را اجرا و سلامت را تأیید کنید. به‌روزرسانی امضاهای ClamAV با profile `signature-updates` فعال می‌شود؛ موفقیت آزمون با امضای همراه image به معنی روزآمد بودن امضا نیست.

۵. مدیر اولیه فقط در نصب خالی ساخته می‌شود. در پایگاه بازیابی‌شده bootstrap اجرا نکنید. مدل و اعلان بیرونی برای نصب ضروری نیستند.

## پشتیبان هماهنگ و محرمانه

```bash
.venv/bin/python tools/installation_backup.py backup \
  --project didban-organization --env-file .env \
  --output /secure-backups/organization-2026-10-25.didban
```

- برنامه از شما گذرواژه پشتیبان حداقل ۱۶ کاراکتر با ورودی پنهان می‌گیرد؛ آن را در argv، shell history یا کنار خود فایل ننویسید. بازیابی بدون این گذرواژه ممکن نیست. خروجی با AES-256-GCM و کلید مشتق‌شده با Scrypt رمز و احراز اصالت می‌شود؛ نوشتن خروجی موجود رد می‌شود.
- در یک پنجره نگهداری، ابزار وب، API و worker را متوقف می‌کند؛ گرفتن backup توقف کوتاه سرویس ایجاد می‌کند. فقط سرویس‌هایی که پیش‌تر در حال اجرا بودند، در پایان یا خطا دوباره شروع می‌شوند. شروع خودکار مجدد توسط ابزار بیرونی را در این پنجره غیرفعال کنید.
- قفل migration تا پایان کپی نگه داشته می‌شود. اتصال مالی/هویتی فعال دیگر، شروع مجدد writer یا اختلاف محیط زنده با تنظیمات حل‌شده، backup را رد می‌کند. override پنهان مانند DSN جداگانه نیز رد می‌شود. مدیر DB نباید خارج از این پروتکل هم‌زمان داده یا storage را تغییر دهد.
- dump پایگاه، تمام فایل‌های خصوصی ورودی و خروجی، secretهای لازم بازیابی و تعریف کامل و حل‌شده Compose در بسته رمز‌شده قرار می‌گیرند. مسیرهای bind تنظیماتِ فایل معمولی همراه بسته ذخیره می‌شوند؛ volume/network خارجی یا مسیر bind پوشه‌ای به برنامه بازیابی جداگانه نیاز دارد. image واقعی و مجموعه/hash مهاجرت‌های اعمال‌شده باید یکسان باشند.
- مسیرهای فایل، پیوند نمادین، checksum تمام اعضا و SHA فایل‌های اصلی/خروجی‌های آماده بررسی می‌شوند. پوشه موقت با دسترسی محدود ساخته و پس از پایان پاک می‌شود؛ فایل نهایی مجوز ۶۰۰ دارد. فضای موقت متناسب با حجم DB و فایل‌ها لازم است.
- پشتیبان قدیمی به‌طور خودکار حذف نمی‌شود. محل جدا از سرور، کنترل دسترسی، نسخه دوم و سیاست نگهداری پشتیبان را سازمان تعیین کند. تنظیم نگهداری محصول جای سیاست نگهداری backup نیست.

## بازیابی بدون دست‌زدن به نصب موجود

```bash
.venv/bin/python tools/installation_backup.py restore-new \
  --bundle /secure-backups/organization-2026-10-25.didban \
  --destination /secure-recovery/rehearsal-2026-10-25
```

ابزار فقط پوشه جدید و پروژه تصادفی `didban-restore-*` می‌سازد. هیچ گزینه‌ای برای overwrite پروژه/پایگاه موجود ندارد. وجود container/volume قبلی در مقصد باعث امتناع می‌شود و نباید cleanup آن منابع را حذف کند. خرابی یا گذرواژه نادرست پیش از اجرای SQL رد می‌شود.

بازیابی با تعریف کامل خود نسخه پشتیبان و imageهای ثبت‌شده انجام می‌شود؛ imageهای دقیق باید از قبل در سرور بازیابی موجود باشند. از تنظیمات فعلی مخزن یا shell به‌عنوان جایگزین secretهای پشتیبان استفاده نمی‌شود. نام volume/network مبدأ حذف می‌شود تا منابع مقصد تازه باشند. ابتدا فقط PostgreSQL و فایل‌های خصوصی ساخته می‌شوند؛ API، worker و وب شروع نمی‌شوند. پس از restore، تعداد رکورد تمام جدول‌های برنامه، hash مهاجرت‌ها، runtime و تمام فایل‌های دارای مرجع دوباره بررسی می‌شوند.

در پوشه مقصد، `recovery.env` و `recovery.compose.json` و فایل‌های تنظیمات خصوصی با دسترسی محدود باقی می‌مانند. تعریف Compose نیز secret واقعی دارد و باید مثل `.env` محافظت شود. در شکست بازیابی، فایل‌های plaintext ساخته‌شده توسط این اجرا پاک می‌شوند؛ نصب مبدأ تغییر نمی‌کند.

پس از بررسی دامنه، پورت‌های آزاد، TLS، اسکنر و تنظیمات مقصد، اپراتور می‌تواند همان پروژه تصادفی و فایل `recovery.compose.json` را شروع کند. ابتدا در محیط تمرینی ورود، عضویت‌ها، شواهد، دانلود و سابقه تأیید را بررسی کند؛ سپس انتقال واقعی سرویس با برنامه سازمان انجام شود. شروع دوباره migration روی نسخه بازیابی‌شده باید فقط با image مطابق/ارتقای آزمایش‌شده باشد. گواهی TLS و تنظیم reverse proxy بیرون این bundle هستند. جایگزینی نصب اصلی در این کار انجام نشده است.

## ظرفیت و پیشنهاد منابع

هدف محصول تا پنج استفاده‌کننده هم‌زمان و ده فایل/حدود بیست هزار ردیف است. `capacity-validation.json` مرجع اندازه‌گیری واقعی است؛ تعداد ردیف فیزیکی، ردیف مالی و نوع بار از هم جدا ثبت می‌شوند. آزمون `test_capacity_runtime.py` پنج هویت واقعی با بارگذاری هم‌زمان، اسکن ClamAV، تفسیر و محاسبات بانکی دقیق و سپس گزارش/دانلود را اجرا می‌کند. این آزمون، پنج تحلیل سنگین هم‌زمان یا همه چیدمان‌های نرم‌افزارهای حسابداری نیست.

پیشنهاد اجرایی اولیه برای آزمایش سازمانی: Linux 64-bit، چهار vCPU، هشت گیگابایت RAM و SSD صد گیگابایت؛ فضای نهایی با حجم فایل‌های نگهداری‌شده و نسخه دوم backup تعیین شود. این اعداد پیشنهاد مهندسی‌اند و مشخصات تضمین‌شده یا نتیجه benchmark روی سرور سازمان نیستند. همین بار مصنوعی باید روی سرور واقعی دوباره اندازه‌گیری و فضای DB/storage پایش شود. عدد ظرفیت یا موفقیت آزمون محلی جای تأیید مالی و نصب سازمانی را نمی‌گیرد.


## نتیجه آزمون ظرفیت و بازیابی — ۲۰۲۶/۱۰/۲۶

آزمون کامل پنج کاربر، ده CSV و بیست هزار ردیف فیزیکی تا تولید و دانلود هر سه خروجی موفق شد: ۱۹٬۹۹۰ ردیف بانکی استاندارد و ۱۹٬۹۸۰ حرکت؛ نقد دقیق ۲۹٬۹۸۰ ریال و سود به‌علت نبود دفتر ناموجود ماند. زمان کل آزمون حدود ۱۷۶ ثانیه بود؛ محاسبات اصلی ۱۰۴٫۴ ثانیه، تحلیل بخش‌ها ۳۴٫۶ ثانیه و تولید/دانلود خروجی‌ها حدود ۲۹ ثانیه طول کشید. بیشترین حافظه همان فرایند آزمون ۷۱۵٫۷ MiB بود؛ مصرف PostgreSQL، اسکنر و کل سرور در این عدد نیست. این اندازه‌گیری روی میزبان توسعه و هم‌زمان با آزمون‌های دیگر انجام شد؛ تضمین زمان پاسخ یا حداقل RAM نصب نیست. پنج خواندن هم‌زمان نتیجه نیز موفق بودند.

بازیابی فعلی با ۱۷ مهاجرت و runtime ۱۰، ۹۴ جدول و ۹ فایل دارای مرجع در دو PostgreSQL مستقل موفق شد؛ هر سه خروجی، تأیید گزارش، بایگانی منبع و جداسازی دسترسی شرکت پس از بازیابی بررسی شدند. این نتیجه به معنی اجرای پاک image یا HTTPS سازمان نیست. شاهدها: `capacity-validation.json`، `restore-validation.json` و `installation-wave3-validation.json`.
