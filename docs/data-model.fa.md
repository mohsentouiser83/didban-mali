# مدل داده ساخت تازه — قرارداد ۰٫۱

افزونه ۲۰۲۶/۱۰/۲۹ با مهاجرت‌های افزایشی ۰۲۴–۰۳۱ در پایگاه موقت تازه ۱۲۲ جدول app دارد. نسخه پروتکل runtime همچنان ۱۰ است و با تعداد migration یکی نیست. مجوز مستقل و سابقه/تنظیم ماژول، نظر/پیشنهاد/تأیید ورودی، کارکنان/قرارداد/کارکرد/قواعد/بررسی قانونی/محاسبه/پرداخت/ورودگروهی/ارتباط مالی و تحلیل/پیگیری/اعلان به schema افزوده شده‌اند؛ جدول‌ها شرکت‌محور و دارای کنترل دسترسی و تاریخچه‌اند. ثبت پذیرش مستقل قانونی از runtime قابل نوشتن نیست. جزئیات و فهرست جاری در `contracts/runtime-extensions.json` و اسناد اجرایی حوزه‌هاست؛ بندهای عددی پایین تاریخچه‌اند.

این سند همراه baseline ثابت `database/001_schema.sql`، `002_guards.sql` و `003_consistency.sql` مبنای پیاده‌سازی است. migrationهای 004/005 مرز هویت، activation، نسخه نشست، شمارنده تلاش و replay/receipt را اضافه کرده‌اند. baseline دارای ۷۵ جدول و app فعلی ۷۷ جدول است؛ جدول ثبت migration در schema مستقل metadata قرار دارد. جزئیات تکمیلی در `contracts/runtime-extensions.json` است. پایگاه سازمانی نصب نشده است.

## مرزها و مالکیت داده

نصب متعلق به یک سازمان است؛ شرکت‌ها داده مستقل دارند. داده عملیاتی/مالی `company_id` و کلید یکتای `(company_id,id)` دارد. ارجاع بین دو موجودیت مالی کلید خارجی مرکب دارد؛ دانستن UUID شرکت دیگر مجوز ارتباط نیست. شناسه منبع مانند `00001` متن است و از UUID داخلی جدا می‌ماند.

جدول‌های هویت، تنظیمات نصب، تعرفه و بودجه کل نصب عمداً global هستند و به نقش عمومی مالی grant نشده‌اند. مدیر نصب بدون عضویت شرکت دسترسی ضمنی مالی ندارد. هزینه API به USD ثبت می‌شود؛ این استثنا مربوط به هزینه عملیاتی مدل است و پشتیبانی مالی ارز خارجی محسوب نمی‌شود.

## پول و تاریخ

واحد کانونیکال IRR است؛ ریال/تومان خام در تفسیر و اصل منبع حفظ می‌شود. تبدیل تومان دقیقاً ضرب در ۱۰ است. ورودی ارزی `unsupported_currency` و واحد نامعلوم مسئله‌ای مستقل است. استفاده از float برای محاسبه یا تبدیل به Number در مرورگر ممنوع است.

نوع `app.money_irr`، دامنه‌ای روی NUMERIC بدون scale اجباری است؛ بیش از ۳۲ رقم صحیح، بیش از شش رقم اعشار، NaN و Infinity را رد می‌کند. این انتخاب جزئیات پیشنهادی `numeric(38,6)` را اصلاح می‌کند: درج مستقیم در ستون دارای scale می‌تواند قبل از CHECK گرد شود. دامنه، مقدار را پیش از چنین گردکردنی رد می‌کند؛ محدوده مفهومی همان ۳۸/۶ است. این رفتار در آزمون دقت بررسی شده و با [مستند رسمی NUMERIC](https://www.postgresql.org/docs/14/datatype-numeric.html) سازگار است.

تاریخ مالی `date` و زمان رویداد `timestamptz` است. اتصال‌ها زمان را به UTC تنظیم و نمایش با منطقه شرکت Asia/Tehran انجام دهند. بازه شامل ابتدا و انتهاست. تاریخ افتتاح، سند، بانک، سررسید، تسویه و snapshot مستقل‌اند. تاریخ قابل مشاهده در فایل، پوشش دوره را اثبات نمی‌کند.

## هویت و نسخه

`source_file` در هر شرکت با SHA-256 یکتا است؛ استفاده مجدد در session با `session_files` انجام می‌شود، نه تولید رویداد مالی دوباره. فایل هم‌پوشان تا تعیین تکلیف خارج از داده فعال است. رکورد منطقی با namespace منبع و شناسه واقعی معامله مشخص می‌شود؛ نام/مبلغ مشابه هویت معامله نیست.

در هر dataset revision برای یک logical record فقط یک record revision انتخاب می‌شود. پس از seal، عضویت رکورد و پوشش منبع تغییر نمی‌کند. اصل و رکوردهای مالی، نقش‌های نسخه‌دار و تصمیم‌ها به‌جای overwrite تاریخچه دارند. اصلاح مبلغ ورودی با فایل تازه است؛ فرم برنامه پرداخت منبعی جداست.

manifest به dataset، دوره، تاریخ مبنا، نسخه سیاست، نقش حساب، نگاشت، ارتباط بانک و تصمیم‌ها متصل است. hash آن از serialization کانونیکال و ترتیب پایدار همین وابستگی‌ها ساخته شود. query خروجی فقط همین انتخاب را بخواند؛ نوشتن hash کنار query زنده کافی نیست. شاخص محاسبه‌شده، شاهد و روز پیش‌بینی بعد از publish تغییر نمی‌کنند. گزارش و تأیید append-only هستند.

## قواعد مهم دامنه

- دفتر و فاکتور دو مبنای مستقل‌اند. اختلاف فقط برای تجارت/طرف/تاریخ/واحد/پوشش متناظر است؛ کل بدهی شامل وام، حقوق و مالیات با فاکتور خرید مقایسه نمی‌شود.
- سند حسابداری در زمان commit حداقل دو آرتیکل با مجموع بدهکار/بستانکار برابر دارد. سند ناقص در staging/خطای منبع می‌ماند؛ برای ثبت بخش سالم، تکه سند نامتوازن وارد دفتر قطعی نشود.
- bank anchor شامل cutoff آغاز یا پایان روز است. همان گردش قبل از cutoff دوباره اضافه نشود. انتقال داخلی خنثی و کارمزد مستقل است؛ تشخیص انتقال صرفاً با مبلغ مساوی قطعی نیست.
- snapshot وصول و رویدادهای شامل‌شده رابطه صریح دارند؛ مبلغ دو بار کسر نشود. ظرفیت تخصیص فعال، پس از برگشت‌های معتبر، در بانک/رویداد/فاکتور زیر قفل کنترل می‌شود. جهت، طرف، نسخه فعال و تعدیل مؤثر را service نیز اعتبارسنجی کند.
- برنامه و فاکتور یک تعهد به `obligation` واحد اشاره کنند. پرداخت واقعی از مانده همان تعهد کم شود؛ جمع invoice+plan+recurrence مجاز نیست. پیشنهاد تکرار تا تأیید اثر ندارد.
- مالیات خالی null است؛ صفر فقط مقدار معلوم است. snapshot مؤدیان خودکار فاکتور یا رویداد پرداخت نمی‌سازد. زنجیره نامطمئن اثر مالی قطعی ندارد.
- status شاخص از status session جداست: available، limited، estimated و unavailable. مقدار unavailable حتماً null و دارای reason code است. صفر واقعی مقدار available می‌تواند باشد. شواهد و coverage مستقل نگه داشته شوند.

## مرز ضمانت SQL و service

SQL اجراشده، FK مرکب، RLS، precision، immutability، ظرفیت، توازن، نقش اعطای مجوز و شرط‌های پایه را کنترل می‌کند. کیفیت شواهد نقش حساب، معنای جمع‌ها، تشخیص معامله، تاریخ مؤثر تعدیل، انتخاب نسخه فعال، کفایت پوشش/سابقه و جلوگیری از ادعای مالی نادرست، وظیفه موتور و کنترل‌های مستقل service هستند؛ وجود JSON کنترل با status=passed صحت واقعی آن کنترل را ثابت نمی‌کند.

RLS مطابق [مستند رسمی PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) مرز شرکت است؛ جای مجوز هر عملیات API نیست. trusted server پس از احراز هویت در هر تراکنش `SET LOCAL app.user_id` و `app.company_id` را تنظیم می‌کند. این مقادیر از body یا هدر دلخواه کاربر گرفته نشوند. runtime حق مالکیت جدول/BYPASSRLS/TRUNCATE یا اتصال ممتاز نصب را نداشته باشد.

قواعد حذف D06 از اصل و سوابق تاریخی محافظت می‌کنند. منبع parse‌شده یا استفاده‌شده عموماً وابستگی تاریخی دارد و بایگانی می‌شود؛ امکان حذف قطعی همه سوابق وعده داده نشده است. حذف فیزیکی فقط برای منبع فاقد وابستگی و پس از کنترل تراکنشی و تأیید صریح است؛ storage deletion با outbox قابل بازیابی اجرا شود.

## وضعیت آزمون

نسخه محلی PostgreSQL 14.21 برای آزمون این طرح استفاده شد؛ نسخه نصب سازمانی باید جدا انتخاب، قفل و آزموده شود. این بررسی، benchmark یا توصیه استقرار همان نسخه محلی نیست. جزئیات در `database-validation.json` و دامنه‌های اجرا‌نشده در سند وضعیت آمده‌اند.

در مرحله اجرایی هویت، نصب پاک Compose روی PostgreSQL 18.6 نیز با migration runner، loginهای محدود و درخواست TCP آزموده شد؛ جزئیات در `compose-validation.json` است. نشست‌ها و tokenها hash دارند، replay حساس رمز‌شده است و رمز کاربران Argon2id است. این آزمون، ارزیابی بار یا صحت کل موتور مالی نیست.

## افزوده مرحله آماده‌سازی — ۲۰۲۶/۱۰/۲۵

نسخه اجرایی ۶ با migration افزایشی 006 شامل metadata آماده‌سازی فایل، امضای اسکن، lease/token صف، پیشرفت واقعی و محدودیت دوره وابسته است. baseline بازنویسی نشده؛ جدول‌های برنامه همچنان ۷۷ هستند. جزئیات در `intake-runtime.fa.md` و `contracts/runtime-extensions.json` است.

## مرحله تفسیر ورودی — ۲۰۲۶/۱۰/۲۵

runtime نسخه ۷ با migration افزایشی 007، شامل ۷۹ جدول برنامه و ۴۶ عملیات فعال است؛ قرارداد کامل ۸۰ مسیر، ۹۷ عملیات و ۱۵۲ schema دارد. تفسیر کنترل‌شده، داده استاندارد تغییرناپذیر، اصلاح نسخه‌دار تنظیمات، سؤال‌های ضروری و شواهد ردیف اجرا شده‌اند. مرجع فعلی [راهنمای تفسیر](interpretation-runtime.fa.md) و گزارش‌های جدید اعتبارسنجی است؛ وضعیت آماده‌سازیِ صرف در بخش‌های قبلی تاریخی است.

`interpretation_finished_at` آماده‌بودن داده برای بررسی است، نه پایان محاسبات مالی. این مرحله manifest مالی، شاخص، ثبت دفتر، تخصیص یا فراخوانی مدل نمی‌سازد. قالب ناشناخته به نگاشت صریح می‌رسد؛ اظهار پوشش جای کنترل مستقل نیست. نسخه‌های قبلی و actor واقعی تصمیم‌ها حفظ شوند. گام بعد، محاسبه قطعی و فعال‌سازی dataset/manifest با جلوگیری از اثر دوباره منابع است.


## افزونه اجرایی محاسبات پایه — 008

نسخه runtime اکنون ۸ است و مدل پایه ۷۵جدولی در 001–003 حفظ شده است. افزونه‌های 004–008 در مجموع ۸۱ جدول برنامه دارند. `dataset_file_selections` انتخاب immutable تفسیر هر فایل در dataset مهرشده و `company_dataset_heads` اشاره‌گر اتمی نسخه فعلی شرکت را نگه می‌دارند؛ کلید مرکب، سازگاری شرکت و فایل/تفسیر و ردیف استاندارد/ردیف منبع را کنترل می‌کند. `processing_sessions.financial_context` اظهارهای مقید به اثرانگشت مجموعه ورودی و هویت پاسخ‌دهنده را نگه می‌دارد؛ `financial_finished_at` و `manifest_id` پایان محاسبات پایه را مشخص می‌کنند. انتشار پایه هنوز پایان pipeline کامل نیست. `result_manifests.forecast_policy_id` تا وجود پیش‌بینی واقعی nullable است. جزئیات در financial-runtime.fa.md و runtime-extensions.json ثبت است.

## وضعیت جاری موج سوم — ۲۰۲۶/۱۰/۲۶

این بخش بر وضعیت‌های تاریخی پیشین مقدم است. runtime۱۰ با migrationهای ۰۰۱–۰۱۷، ۹۴ جدول برنامه و ۱۰۴ عملیات ثبت‌شده HTTP اجرا می‌شود؛ قرارداد کامل ۹۸ مسیر، ۱۱۹ عملیات و ۱۷۸ schema دارد. ثبت endpoint به‌تنهایی آزمون کامل آن نیست.

گزارش ثابت پس از تحلیل، نسخه دقیق manifest، تطبیق‌ها، تسویه، نقدینگی، پیش‌بینی و شواهد را نگه می‌دارد و سه کار بادوام PDF، Excel و CSV خطا می‌سازد. `analysis_finished_at` پایان تحلیل است؛ پایان نوبت فقط پس از آماده‌شدن هر سه خروجی و رفع مانع سؤال ثبت می‌شود. `report_id` روی نوبت و لینک همان گزارش در رابط موجود است. تأیید با مجوز جاری و همان نسخه ثبت می‌شود و به نسخه تازه منتقل نمی‌شود. نوبت تمام‌شده دوباره باز نمی‌شود؛ بازبینی پیش‌بینی نوبت ادامه مستقل دارد.

صفحات مستقل گزارش‌ها، سیاست‌ها و اصل فایل متصل‌اند. سقف بارگذاری و فرض پیشنهادی پیش‌بینی نسخه‌دار و مصرف می‌شوند؛ بایگانی اثر مالی و شواهد را حفظ می‌کند. مدت نگهداری بدون پاک‌سازی خودکار است؛ حذف قطعی تنها برای اصل واقعاً فاقد وابستگی، با مجوز و پاک‌سازی فیزیکی بادوام انجام می‌شود. جزئیات در `reports-runtime.fa.md` و `policy-retention-runtime.fa.md` است.

پشتیبان رمز‌شده، تنظیمات HTTPS و بازیابی در مقصد تازه در `installation-readiness.fa.md` شرح داده شده‌اند. آزمون بازیابی برنامه فعلی روی دو PostgreSQL مستقل، مدرک نصب پاک Compose نیست. `capacity-validation.json` وضعیت واقعی آخرین اندازه‌گیری را نشان می‌دهد؛ پنج استفاده‌کننده در یک بسته بانکی مصنوعی به معنی پنج تحلیل سنگین هم‌زمان نیست. ساخت image پاک به اختلال دریافت بسته‌ها متوقف شده و TLS واقعی سازمان هنوز بررسی نشده است.

گزارش‌های `reports-validation.json`، `report-rendering-validation.json`، `policy-validation.json`، `delivery-workflow-validation.json`، `backup-bundle-validation.json`، `installation-config-validation.json` و `restore-validation.json` شواهد این مرحله‌اند. ظرفیت کامل و بازیابی با ۱۷migration موفق‌اند؛ اجرای نهایی یکپارچه و حالت‌های باقی‌مانده مرورگر در حال به‌روزرسانی‌اند؛ وضعیت pass/fail و hash هر گزارش مرجع همان دامنه است. `wave2-validation.json` و گزارش‌های نصب مراحل قبل، شاهد نسخه فعلی همه قابلیت‌ها نیستند. مدل زنده و provider برای تشخیص فایل/نگاشت/نقش حساب، ارزیابی قالب‌های متنوع، کاهش حرکت واقعی سیستم‌عامل و پذیرش مالی/سازمانی همچنان باقی‌اند. هیچ پیام بیرونی، نصب روی سازمان یا فراخوانی مدل زنده انجام نشده است.

جزئیات افزونه‌های ۰۱۳–۰۱۶: `report_snapshots` دارای اثرانگشت ورودی، شماره نسخه، نوبت تولید و دامنه ready/limited است؛ `export_jobs` مالک فعلی تولید، lease/token، تعداد تلاش، خطا و اندازه فایل دارد و خروجی ready تغییرناپذیر می‌ماند. چهار جدول تازه `policy_configuration_events`، `retention_settings`، `source_lifecycle_events` و `source_deletion_jobs` شرکت‌محور و دارای RLS هستند. نگهبان وابستگی منبع در SQL و خدمت اجرا می‌شود. ۰۱۵ runtime۱۰ و منع بازکردن نوبت terminal را ثبت می‌کند؛ ۰۱۶ ایندکس جست‌وجوی ردیف استاندارد و lease محدود ده‌دقیقه‌ای تحلیل با همان کنترل token/fence/barrier را می‌افزاید. فهرست کامل افزونه در `contracts/runtime-extensions.json` است؛ baseline ۷۵جدولی بازنویسی نشده است.

افزونه ۰۱۷ ثبت تعرفه تاریخی مدل را برای providerهای `openai` و `avalai` جدا می‌کند؛ درخواست‌های قبلی و runtime۱۰ تغییر نمی‌کنند. این توضیح ساختار، تأیید فراخوانی زنده Avalai یا کیفیت آن نیست.

## توسعه گزارش مدیریتی — ۲۰۲۶/۱۰/۲۶

مهاجرت افزایشی `022_statement_account_roles.sql` فقط قید نقش حساب را برای دارایی ثابت، سایر دارایی‌ها، کاهنده دارایی و سایر حقوق مالکانه گسترش می‌دهد؛ جدول تازه‌ای اضافه نمی‌کند. داده و سوابق قبلی حفظ می‌شوند. گزارش‌های مدیریتی و قالب صریح حساب‌ها در محتوای تغییرناپذیر `report_snapshots` نگه داشته می‌شوند؛ تاریخ/قالب تازه، نسخه گزارش تازه با تأیید مستقل می‌سازد. محتوای schema۳ می‌تواند `management`، `report_scope` و `manifest_metrics` داشته باشد؛ مقادیر بازه سفارشی از شاخص‌های مرجع manifest جدا می‌مانند. ## ادامه گزارش‌های مدیریتی — ۲۰۲۶/۱۰/۲۶
